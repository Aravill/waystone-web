# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Waystone Web: Go (stdlib `net/http`, SQLite via `modernc.org/sqlite`, local username/password auth) backend + plain HTML/JS frontend in `./static` (no build step; Alpine.js vendored at `static/vendor/`). MVP scope and progress: `docs/mvp.md`.

## Commands

- `.env.example` must list every env var the code reads (`os.Getenv`), with required/optional and defaults. Update it whenever you add, rename, or remove one, and keep `docker-compose.yml`'s `environment:` in sync.
- Run locally: `go run main.go` → http://localhost:8080. Set `SESSION_SECRET` (required, ≥32 chars, e.g. `openssl rand -base64 32`; the server exits without it) and `ADMIN_PASSWORD` per `.env.example`; without `ADMIN_PASSWORD` the server starts but the admin can't log in. Add `SEED_DEMO_DATA=1` to get demo users/campaigns/sessions on an empty DB (users `testy`/`roy`/`adam`/`simon`, password in `config.InitialPasswords`); off by default, local dev only.
- Verify changes: `go build ./... && go vet ./...`. Frontend E2E tests use Playwright in `e2e/`: `npm ci`, `npx playwright install chromium` (once), `npm run test:e2e`. They start their own server on port 18080 with a throwaway DB in `e2e/.tmp` (via `DB_PATH`) and never touch `./data`. PRs to `main` can't merge unless the `playwright` check (`.github/workflows/e2e.yml`) passes. There are no Go tests or linters; add E2E tests only for stable, high-value flows.
- `./deploy.sh` deploys production (app + Caddy HTTPS for waystone.aravill.org via `docker compose --profile prod up -d --build`) and keeps the data volume; never run `docker compose down -v` against data worth keeping (it wipes the SQLite volume). SQLite snapshots go to `./backups` (`BACKUP_DIR`).
- For local Docker testing use `/deploy-local` (`up`/`down`/`status`), not `docker compose up`: plain compose names the project after the folder, so every worktree leaves its own image and volume behind.
- Static files are copied into the Docker image, so frontend changes need `docker-compose build --no-cache`.
- Local DB lives at `./data/waystone.db` (gitignored); `DB_PATH` overrides it.

## Architecture gotchas

- Routes are registered in `api/router.go` (not `main.go`, despite the README). `/` is auth-wrapped and serves `dashboard.html` (Home, fed by `GET /api/agenda` in `api/agenda.go`), so every root-level JS/CSS file a page loads must get its own `http.HandleFunc` entry there, or be referenced under `/static/...`. Home also loads `/campaigns.js` for the shared helpers (`replyWord`, `zoneAbbr`, `formatShortDate`, `userAvatarHtml`).
- App version is baked in at build via ldflags (`config.Version`, `APP_VERSION` build arg). The Deploy workflow computes it from the PR-title prefix (`feat/` bumps minor, else patch) and tags after a successful deploy, so keep the `feat/` prefix accurate.
- DB access goes through the `Store` interface in `db/store.go`: add the method to the interface, implement it on the SQLite store, and expose a package-level wrapper in `db/` that calls `GetStore()`.
- Protect routes with `middleware.AuthMiddleware`; use `middleware.GetSession()` / `ClearSession()` for session state.
- Accounts start with no password (`password_hash=''`, `must_change_password=1`). Admin create and reset call `issueInvite`, which returns a one-time token valid for 7 days; only its SHA-256 hash is stored in `password_invites`, one per user. `/invite/` and `/api/invite/` are public, outside `AuthMiddleware`. An invite is valid because its row exists, never because of `must_change_password`, and `/change-password` only remains for users still holding an old temporary password.
- `AuthMiddleware` adds `?next=<page>` when redirecting a logged-out page request, and `login.html` only follows it if it's same-origin. Page loads (not API calls) renew the session cookie at most once a day via `renewed_at`.
- User display name precedence: `Nickname` → `Name` → `Username` (`User.DisplayName()`). API responses that reference users keep raw IDs and add enriched `*_user` / `*_users` objects (mirror the campaigns API).
- Session responses are one per `(session_id, user_id)` (upsert); pending players are computed from the campaign's player list.
- When changing `models/user.go`, update seed data in `config/config.go` and keep `SaveUser` and the `SELECT`/`Scan` sites in `db/sqlite_store.go` in sync.
- The `ADMIN_USERNAME` user is env-managed: password reset from `.env` on every start; can't be blocked, deleted or demoted.
- The session cookie is `Secure` by default (`SESSION_COOKIE_SECURE`): fine on `http://localhost`, but over plain HTTP on a LAN IP login returns 200 and the cookie silently never sticks; set it to `false` there.
- The game journal is codex pages: a played session's entry is an ordinary page (`kind` `lore`) with `pages.session_id` set (unique index `idx_pages_session`, created after the ALTER), so it has links, tags, history and follows normal codex rights (See reads, only Edit on the codex writes; being in the game gives no right). The session number is never stored (numbers are positional, `campaignSessionSummaries`): titles are `{game}: {YYYY-MM-DD}` (migrated entries add ` – {name}`, duplicates ` (n)`), set once and never renamed, and the page payload's `session` object (`journalSessionPayload`: `campaign_id`, `campaign_title`, `session_id`, `number` or null unless played, `date`, `status`, `played`, `attendees`) is computed per request, so the page shows "Session N" at read time. Entries exist only for played sessions (Confirmed and ended, or by hand): `journalSession` in `api/journal.go` is the one check. The only write route is `POST /api/campaigns/{id}/journal/{sid}` (201 `{page:{id}}`, 200 for the existing page, 409 `session_not_played` / `no_codex`, 403 without Edit on the game's codex); it needs a codex on the game (`campaigns.codex_id`), finds the folder `{game}: Campaign Journal` by `campaigns.journal_folder_id` (db-internal, not in `models.Campaign`) or makes it at the codex's top level with default template `builtin:session`, and starts the page from the folder's (or nearest ancestor's) template with `{{date}}` = the session's date (`fillTemplateOn`). The folder is an ordinary folder: rename, move or delete it freely; if it's gone the next entry makes a new one (" (2)" on a sibling name clash). A game rename renames it only while it still has the generated name and the new name is free (`RenameJournalFolder`); page titles never change. Changing or clearing the game's codex moves nothing and clears `journal_folder_id`; old pages keep their `session_id` and the game page still lists them (`GetJournalPages`, `can_open` false shows "Written · in {codex}"). Foreign keys are off: `DeleteManualSession` and `DeleteCampaign` keep the pages and set `session_id = ''` by hand (so they become ordinary pages), `DeleteCodex` clears the games' `journal_folder_id`. A cancelled session's page stays linked and editable and is listed under "Journal pages of cancelled sessions" (`journal_cancelled`). Old `/games/{id}/journal/{sid}[/edit|/history]` URLs answer 303 to the page (`/codices/p/{pageId}/journal[/edit|/history]`) or to the game. The legacy tables `journal_entries`/`journal_revisions`/`journal_contributors` stay until no rows remain (a later cleanup drops them); only `SaveJournalRevision` is still in the `Store` interface, for the seed. `migrateCampaignJournalTx` moves a game's entries into its codex (revision numbers, bodies, `restored_from`, `created_at`, notes plus "Merged with revision N", author and contributors kept; legacy rows deleted, so it is idempotent; entries whose session is gone or already has a page are skipped and kept) from `SetCampaignCodex` (one transaction with setting the codex) and, per game with a codex, at startup (`migrateJournalToCodex`, end of `initSchema`). A game without a codex has no journal: the DM sees "Link a codex in Edit game to keep a journal" and `journal_pending` (legacy entries waiting, DM and admin only). Before deploying, run the build against a copy of the latest `./backups` snapshot and compare entry and revision counts before and after.
- Characters: assignments are ended (`ended_at`), never deleted, on leave/kick/decline/anonymize/swap/clear. Foreign keys are off, so `DeleteCampaign`/`DeleteCharacter` delete assignments by hand, and any new code that removes a player from `campaigns.players` must end their assignments (`endUserAssignments`, same tx). A game accepts characters only when `campaignSystemID` resolves its system text to a known system. `notify` accepts a nil campaign. A character has an optional `codex_url` (set by its owner in the create/edit forms), shown as a "Codex page" button on the character page; `validCodexURL` in `api/characters.go` is the only server check (`https://waystone.aravill.org/codices...` only, exact host, no port/userinfo, or `/codices...` on the local host the request came to, so dev/E2E work; 400 otherwise; saved as `url.URL.String()` with the host lower-cased: path must equal its `path.Clean` form, bar one trailing slash, so `//codices` and `..` are refused; at most 2000 characters after percent-encoding), and `safeCodexUrl` in `static/characters.js` re-checks on the client before rendering a link. Design: `docs/design/characters.md`.
- Session polls: every Suggested non-manual session has a `poll_id` (never empty; a single suggestion is a one-date poll, `SaveSession` fills it). Confirming one date deletes the poll's other Suggested dates and their replies in one tx (replies are deleted by hand: foreign keys are off). "Upcoming" means the start hasn't passed, computed in Go (`sessionStart`), and unanswered counts are polls. The reminder dedupes through `json_extract(data,'$.poll_id')` on `notifications`. The calendar, game page and Home group by `poll_id` with helpers in `campaigns.js`.
- Sessions with `manual=1` (the DM's "Record a past session") are chronicle-only: excluded from the month view and ICS, no replies or notifications, and may have `time=''` so `sessionStart` fails; check `Manual` before calling it.
- The DM can also edit attendance of a played calendar session (`journalSession` says played) through the same `PUT /api/campaigns/{id}/played-sessions/{sid}`: only `attendee_ids` and `guests` are used (date and times never change; DELETE stays manual-only), `SaveSessionAttendance` sets ticked replies to Accepted (inserting a row if needed) and unticked Accepted ones to Declined, with no notifications, and journal pages follow because attendees are computed at read time.
- Repeating polls (`poll_schedules`, one per game; `api/poll_schedule.go`): the minute ticker's `postDuePolls` and the PUT handler both run `postDueCycles` under `pollScheduleMu`, which saves `next_cycle` before posting so a cycle is handled once. The DM notices `poll_posted`/`poll_skipped` use actor ""; the players get an ordinary `session_suggested` from the DM. The Repeat dialog is shared (`repeatDialogMixin` in `campaigns.js`, same `#repeatDialog` markup on the calendar and game pages).
- The Calendar button focuses the first unanswered session's month, so tests use `openCalendar`/`goToMonth` helpers, not `page.clock`.
- `GET /api/notifications` takes `limit` (1-50), `offset` (0-10000) and `unread=1` (only unread) and returns `notifications`, `unread_count` and `has_more`; without `unread` it returns everything, which the E2E specs rely on. The header inbox (`static/notifications.js`) pages 10 at a time and keeps "Only unread" in localStorage `waystone-notif-unread` (on by default).
- `api.StartSessionStartNotifier(ctx)` (started from `main.go`) runs every minute and sends one `session_started` notification per Confirmed session to its players and followers (never the DM) once it begins. The `notifications` table is the dedupe, so there is no schema or env var for it.
- Codices (`/codices`, `api/codex*.go`, `db/sqlite_codex*.go`, `static/codex*.js`): a codex is a folder of pages and every page belongs to one (`pages.codex_id`; there is no Unsorted folder, creating or moving a page needs an existing codex). Old URLs `/codex`, `/codex/w/...` and `/codex/p/...` 301 to `/codices`, `/codices/c/{id}` (a codex) and `/codices/p/{id}/...` (a page); the API is `/api/codices` (`GET` home, `POST` create), `/api/codices/c/{id}`, `/api/codices/pages/...`, `/api/codices/folders/...`, `/api/codices/titles?codex=`. The schema used to say `worlds`/`world_id`: `renameWorldsToCodices` renames them in place before the CREATE block, and `rescueUnsortedPages` moves any page left with `codex_id ''` into a codex named "Unsorted pages". `[[Title]]` links and map pins resolve only inside the page's own codex, by title or alias (compared with `NormName`, never SQL NOCASE), and are stored in `page_links.to_page_id` / `map_pins.to_page_id`. Anything that changes what a name can point at (create, rename, alias set, move, delete a page) must end its transaction with `resolveCodexLinks(tx, codices...)` for the codices it touches (the page's codex; a move passes the old and the new one), and `loadCodexIndex` takes the same optional codex filter, so a save never reloads every codex; a body save only rebuilds that page's rows. Foreign keys are off: `DeletePage` removes revisions, contributors, aliases, links, pins, pin events and images by hand (the handler then removes the image files), and `DeleteCodex` is refused (409 `codex_in_use`) while a page is in it; games don't block it, it clears their `campaigns.codex_id`. `campaigns.codex_id` is a label written only by `SetCampaignCodex`, never by `SaveCampaign`; the game API sends `codex_id` and `codex` `{id, name}` and `game.html` shows it as a label (a link when `codex.can_open`). Maps are hidden for now: `codex.html` doesn't load `codex-map.js` or show any map, pin or games UI, but the tables, the `/api/codices/pages/{id}/...` map routes and the upload/backup code stay. Maps are an optional part of any page, not a page kind: the API sends `has_map` (a startup `UPDATE` folds old `'map'` rows into `lore`; remove it if map becomes a kind). `pages.kind` is `lore` (an article) or `timeline` (set at creation, never changed); a timeline's dated events and calendar live in `timeline_events` and `timeline_calendars` (keyed by the timeline's page id; an event's `linked_page_id` is a page of the same codex or `''`, and an unlinked or orphaned event keeps its title), saved at once with no revisions. Without foreign keys, `DeletePage` removes a timeline's events and calendar and unlinks events elsewhere that pointed at the page, and `MovePage` unlinks both ways (events keep their titles). A page's map is its newest `map_images` row (history ordered `created_at DESC, rowid DESC`), pins are `map_pins`/`map_pin_events` keyed by `map_page_id` (the page), and pins count as backlinks (`via` `pin`). "Remove map" (`DELETE /api/codices/pages/{id}/map`, `RemoveMap`) deletes the pins in one tx, logging a `remove` event each, and inserts a marker `map_images` row with `file=''`: a newest row with an empty file means no map, the marker is hidden from the image list, `DeletePage` skips it, and restoring an older image (a new row) brings the map back, while the removed pins return only by undoing their events in History. Pins, pin undo-of-remove and map removal need a current image (409 `the page has no map`). Folders (`codex_folders`, `pages.folder_id`) nest inside a codex and are only for sorting: links, title/alias uniqueness and revisions ignore them, folder names are unique among siblings by `NormName`, and a page's folder must be in its codex (`MovePage` resets it). folders nest up to 10 levels (`db.MaxFolderDepth`, 400 on create/move beyond it), a missing parent is 400 `parent_not_found` while a missing edited folder is 404 `folder_deleted`, and PUT takes `name` or `parent_id`, not both. `DeleteFolder` re-parents its sub-folders and pages one level up by hand (refused if a sub-folder's name clashes in the parent), and `DeleteCodex` removes the codex's folders. Page saves are optimistic (`base_revision`, 409 `stale_base`), titles change only through rename (which rewrites links in the same codex and adds revisions), and restoring a revision restores the body only. The diff helpers `diffWords`/`tidySegs`/`diffHtml` (for the conflict panel and History) live at the top of `codex.js`; a page inside a folder named `{game}: Campaign Journal` shows in the tree without its `{game}: ` prefix, and a page with a `session` payload shows the eyebrow "Campaign journal · {game}", the heading "Session N" (its title when the number is null) and a strip with the date, who was at the table and a link to the game.
- Codices access rights (admin page `/admin/access`, `api/admin_access.go`): `user_rights (user_id, action)` holds `codices.see` / `codices.edit` (`models.RightCodicesSee`/`RightCodicesEdit`; generic so more actions can be added) and `codex_access (codex_id, user_id, level)` holds `see` or `edit` per codex; admins need no rows and always pass, new users get nothing, and `CreateCodex` inserts its creator's `edit` row in the same tx (not for admins, so no hidden row outlives a demotion) (`DeleteCodex` and `AnonymizeUser` clear them by hand). `api/codex_access.go` is the one place for the rules: `loadCodexRights(userID)` gives a `codexRights` with `canSee/canEdit(codexID)` (edit implies see; nothing without `codices.see`) and `canManage()` (Edit Codices: create codices, rename or delete ones the user can see); handlers call `codexRightsFor` then `checkCodex/checkPage/checkFolder(w, id, edit)`, which answer 404 when the codex or page isn't visible (never leak existence) and 403 when it is visible but not editable (moving a page needs Edit on both codices; an unknown or invisible target is 400 `codex not found`). `codexGate` hides `/codices*` and `/api/codices*` (404 / redirect to Home) from anyone without See Codices, `/auth/current-user` returns `codex_access` from the same check, and `theme.js` reveals the `[data-codex]` links (which start `hidden`) only when it's true. The home, codex and page payloads add `can_create` / `can_manage` / `can_edit` for the UI, `titles`, home and recent changes list only visible codices, and `files/{name}` needs See on the codex of the page that owns the image. A game's `codex` object has `can_open` (the viewer can see it); a DM can only set `codex_id` to a codex they can see. Codex names are unique across all codices, so a 409 `codex_name_taken` tells someone with Edit Codices that a codex of that name exists (accepted). `SEED_DEMO_DATA` grants the demo users See Codices, Edit on the demo codex for Roy and Testy, and Edit Codices for Roy.
- Codices tags (`api/codex_tags.go`, `db/sqlite_codex_tags.go`): `codex_tags (id, codex_id, name, ...)` belong to one codex and `page_tags (page_id, tag_id)` joins them to pages; names are 1-40 characters on one line and unique per codex by `NormName` (409 `tag_name_taken`), anyone with Edit on the codex creates, renames and deletes them (`GET`/`POST /api/codices/c/{id}/tags`, `PUT`/`DELETE /api/codices/tags/{id}` through `checkTag`, `PUT /api/codices/pages/{id}/tags` with `{names}` creates the missing ones), tag changes are not revisions, and cascades are by hand: `DeleteCodexTag` drops its `page_tags`, `DeletePage` drops the page's, `DeleteCodex` drops the codex's tags, and `MovePage` drops the page's tags (they belong to the old codex; the move warning says so). The page payload has `tags`, the codex payload has `tags` with `page_count` and each page's `tag_ids`, and `?tag=name` on the codex screen filters the list client-side.
- Codices pictures (`api/codex_pictures.go`): `page_images (id, page_id, name, file, width, height, uploaded_by, created_at, removed_at)` plus `pages.cover_image_id` (added with the ALTER-if-missing pattern) hold images written `![[name|caption]]` (the caption may be empty); a picture belongs to its page and follows its codex's rights. The routes are `GET`/`POST /api/codices/pages/{id}/pictures` (raw body, original file name URL-encoded in `X-File-Name`, same `receiveCodexImage` as map images: PNG, JPEG, WebP or GIF, 25 MB; `gifFramesFit` walks a GIF's blocks without decoding and refuses frames outside the screen, truncated files and more than 1000 frames, because `DecodeConfig` only reads the screen size), `DELETE .../pictures/{imageID}` and `PUT .../cover` `{image_id}`; they are "pictures" because `.../images` already is the page's map history. `name` is the sanitised file name, unique within the page including removed ones (" (2)" before the extension) and across the page's attachments too (see Codices attachments). Remove is soft (`removed_at`): the row and file stay so old revisions and any `![[name]]` still in the text keep rendering, so the page payload's `image_index` lists every picture ever uploaded by name while `images` lists only current ones; a removed picture can't be the cover and removing the cover clears it. `DeletePage` deletes its picture rows and files. `db.UploadFileRe` (which also gates serving, removal and the backup mirror) accepts `png|jpg|webp|gif`, and `GetImageCodexID` looks in both `map_images` and `page_images`, so `files/{name}` needs See on the page's codex. Options: `![[name|OPTIONS|caption]]` where OPTIONS is a first segment made only of keywords `small|medium|large|full` and `left|center|right` (any case, last of each kind wins, defaults medium/right, `full` is always centred); otherwise everything after the name is the caption (`codexPicOptions`). They only affect a picture alone in its paragraph (classes `cx-figure--{size}`/`--{spot}`); on the page view an editor gets a layout bar on each lone figure (`data-pic` = embed index, counted skipping `{{list}}` lines) that rewrites the embed with `codexSetPicLayout` and saves a revision noted "Picture layout". A line made only of pictures is always its own paragraph (`codexMarkdown` pads it with blank lines), so a picture on its own line is a figure even with text on the next line. Go and the other regexes only ever take the name, so nothing server-side knows about options. `ParseWikiLinks` skips a `[[...]]` that follows `!`, so picture embeds are never links or wanted pages; the JS regexes (`CODEX_LINK_RE`, `CODEX_IMAGE_RE`, the editor's) mirror it, and `codexMarkdown` swaps pictures for placeholders before links.
- Codices attachments (`api/codex_attachments.go`, `api/codex_attachment_check.go`, `db/sqlite_codex_attachments.go`): `page_attachments (id, page_id, name, file, size, uploaded_by, created_at)` hold files of any page kind (articles, journal entries, timelines), up to 100 MB each, no total limit, no history, no notifications; the types are an allow-list by extension (PDF, PNG/JPEG/WebP/GIF, doc/docx/xls/xlsx/ppt/pptx, odt/ods/odp, txt, md, csv, zip, mp3) checked against the content by `attachmentContentOK` (magic bytes; zip-based formats through a size-capped `zip.NewReader`; a password-protected docx/xlsx/pptx is an OLE file and is refused with a hint to put it in a .zip). Routes: `POST /api/codices/pages/{id}/attachments` (raw body, original name URL-encoded in `X-File-Name`, 201 `{attachment}`), `PUT`/`DELETE .../attachments/{attId}` (Replace and Remove), `GET`/`HEAD /api/codices/attachments/{id}[/{name}]` (the `{name}` tail is ignored) and `GET /api/codices/c/{id}/attachments` (every file of the codex with its `page`, plus `total_size`, for the Attachments screen). Rights as for pictures: See reads and downloads, Edit uploads, replaces and removes (`checkPage`). Error codes: `type_not_allowed`, `content_mismatch`, `wrong_extension` (Replace needs the same extension), `too_large` (413), `attachment_not_found`, `page_deleted`. Names are shared with pictures through `pageFileNames` (`NormName`, removed pictures included), and both `AddPageAttachment` and `AddPageImage` use it in one transaction, so a clash gets " (2)" in either direction. Storage: `UPLOAD_DIR/attachments/<uuid>` with no extension (`db.AttachmentDir`, `AttachmentFileRe`); the bare name never matches `UploadFileRe` and the backup mirror only copies top-level image files, so attachments are deliberately not backed up (after a restore a row may point at a missing file: the download is a 404 until someone removes or replaces it). `.upload-*` temp files there older than an hour are removed at first use. Serving: `inline` types (pdf and images) are shown, the rest download as `application/octet-stream`; all get `nosniff`, everything but PDF also `default-src 'none'; style-src 'unsafe-inline'` (a CSP can break the browser's PDF viewer, which runs in its own origin); `Cache-Control: private, no-cache` plus `ETag` = the stored file name, because Replace keeps the URL (so no `immutable`) and the ETag keeps 304 and `If-Range` right. Replace stores the new file under a new uuid, points the row at it (`uploaded_by` and `created_at` become the replacer's and now), and only then deletes the old file; Remove deletes the row, then the file. `DeletePage` returns two lists (picture files, attachment files) and the handler removes both. Upload, download and copy-page extend the read and write deadlines to `attachmentTimeout` (15 min) through `http.NewResponseController`. Text: `![[rules.pdf]]` or `![[rules.pdf|label]]` is a file link with the size; `codexMarkdown` takes a `files(name)` lookup, swaps an embed that is no picture of the page but is an attachment (or has an attachment extension and none is found: "Attachment removed: name") for a `\u0005` placeholder, shares the embed index with `\u0002` pictures (so the layout bar's `data-pic` still counts every `![[ ]]`), and renders it as an inline link, never a figure or gallery; pictures win a name clash in the lookup. Copy page: `copy_attachments` (default off) duplicates each file under a new uuid (`duplicateAttachments`; every failure path removes the pictures and attachments already copied). The page's Attachments box and the Attachments screen (`/codices/c/{id}/attachments`, a last segment like `graph` and `inbox`) are in `codex.js`; uploads go through `codexUpload` (XHR, for progress), the one place that is not `fetch()`. Design: `docs/design/codex-attachments.md`.
- Codices templates and copying (`api/codex_templates.go`, `db/sqlite_codex_templates.go`): `codex_templates (id, codex_id, name, description, body, created_by, created_at, updated_at)` and `codex_template_tags (template_id, tag_id)` join a template to tags of its codex by id, so saving a template creates the tags it names that the codex lacks, `DeleteCodexTag` drops the join rows, and `DeleteCodex` deletes the codex's templates (they never block it). A name is 1-80 characters, unique per codex by `NormName` in Go (409 `template_name_taken`); the description is at most 160, the body is limited like a page's, and templates have no history. Anyone with Edit on the codex creates, edits and deletes them (`GET`/`POST /api/codices/c/{id}/templates`, `PUT`/`DELETE /api/codices/templates/{id}`; See lists them). The nine built-in templates are Go data (`builtinTemplates`, ids `builtin:session` and so on, the same in every codex, never stored); `GET /api/codices/templates/builtin` returns them with `today`. `POST /api/codices/pages` takes `template_id` (a built-in, or a template of the same codex, else 400): the server then ignores `body` and writes the template's text and tags in one transaction (`CreatePageWith`). `{{title}}` and `{{date}}` (written "Jan 2, 2006", UTC) are the only placeholders, filled in one pass by `fillTemplate` (the client's `fillTpl` mirrors it for the preview, using the server's `today`). "Save as template" is computed in the browser (`codexHeadingsOnly`: the `##`/`###` lines outside code fences; or all the text without `![[...]]` pictures) and posted to the template endpoint. `POST /api/codices/pages/{id}/copy` needs See on the source and Edit on the target (an unseen target is 400 `codex not found`, a see-only one 403): the copy is a new page with its own history starting at revision 1 with the note "Copied from <title>", without aliases, with `[[links]]` as written (resolved in the target codex by the create transaction), the tags by name with `copy_tags` (missing ones created), and with `copy_images` each current picture's file duplicated under a new random name (`duplicatePictures`; picture names and the cover are kept, removed pictures the body still embeds are duplicated too with their `removed_at`, the copier is recorded as uploader, and the new files are removed again if the insert fails; a cheap `CheckNewPage` runs first so a refused copy duplicates nothing). Built-in template names are reserved: creating or renaming a template to one is a 409 `template_name_taken`. A folder has a default template (`codex_folders.default_template`, added by ALTER-if-missing; `PUT /api/codices/folders/{id}` `{default_template}`, one field per request like `name`/`parent_id`): `''` none, `builtin:<id>`, or a template id of the folder's own codex (else 400), set from the folder menu's "New pages start from…". The New page dialog preselects, in order: a template passed in (the templates dialog's Use), the folder's default or the nearest ancestor's (`codexFolderDefault`), then the last one used in the codex; changing its folder select re-picks unless a card was already clicked (`tplTouched`). Missing links and wanted pages go through the same dialog, so they follow it; timeline "Create a page for it" stays `builtin:event`. `DeleteCodexTemplate` clears the default of folders using the template in the same tx. The New page dialog has no codex select (it creates in the current codex) and remembers the last template per codex in localStorage.
- Codices graph (`api/codex_graph.go`, `db/sqlite_codex_graph.go`, `static/codex-graph.js`): `GET /api/codices/c/{id}/graph` (See right, 404 otherwise) returns `nodes` (pages plus a synthetic `missing:<normalized text>` node, `missing: true`, per link target without a page, with top folder, folder path, tag names and a plain excerpt), `links` (`source`, `target` from `page_links`, A to B and B to A both kept; the client draws one line per pair) and `top_folders` (name order, which fixes the colours); it runs three queries and leaves out map pins. The graph screen is `/codices/c/{id}/graph` (`?from={pageId}` rings that page): in `parseRoute` a last segment `graph` right after the codex id always means the graph screen, so codex links never carry a slug (a codex named "Graph" still works). The layout is `d3-force` vendored through `tools/vendor` (it now builds two bundles: `codemirror.bundle.js` and `d3-force.bundle.js`, global `D3F`), loaded lazily by `codex-graph.js` and drawn as plain SVG; node positions are not saved. The page screen's Local graph box (hidden when the page has no links) uses `GET .../graph?around={pageId}`: that page, its direct neighbours in both directions and the links among them, without excerpts (404 when the page isn't in that codex); the client shows at most 30 neighbours.
- Codices drafts (`codexDraft*` in `static/codex.js`): the editor keeps unsaved text only in localStorage, `codex-draft:{pageId}:{base}` = `{body, note, initial, at}` (base is the revision the edit started from; written 800 ms after the last change, no backend). Cleared on save, Discard mine, Cancel and the banner's Discard. A draft on an older base is restored onto that base (`draft.base`/`initial.body`), so Save gets 409 `stale_base` and the existing conflict panel shows the diff; no separate conflict UI.
- Codices tree drag and drop (`codex.js`: `onTreeDragStart` .. `moveTreeItem`): only with Edit and `(pointer: fine)`; it uses its own data type `application/x-codex-item` so the image file-drop handlers (which look for `Files`) ignore it, and it reuses the two move routes (`PUT /api/codices/pages/{id}/folder`, `PUT /api/codices/folders/{id}` with `parent_id`). The client mirrors `db.MaxFolderDepth` (10) in `treeDropOk`/`folderLevels`/`folderHeight`; keep them in step. Touch keeps the folder menu Move and the page Folder > Change. The toast with an Undo button is `showMessage(text, type, {label, run})`.
- Codices live lists (`codexLiveList` / `codexParseList` in `static/codex.js`): a paragraph of its own `{{list key:value ...}}` (values bare or "quoted") in a page body shows a ruled box of matching pages. Keys: `tag:` (repeatable, all must match, by name), `folder:` (a name matches every folder of that name, `Places/Inns` a path from the top; sub-folders count), `links:here` (pages in the page's "Linked from" list), `kind:` (`lore`|`timeline`), `sort:` (`title` default, `updated`/`created` newest first), `limit:` (1-200, default 50, then "and N more"); an unknown key or bad value shows "Unknown list option: x". It is rendered only in the browser: `codexMarkdown` swaps each line (`CODEX_LIST_RE`) for a placeholder and the page getter `listRenderer` builds the box from the codex payload (`pages` carry `created_at`/`updated_at`, `tag_ids`, `folder_id`), leaving out the current page; without a renderer (history revisions, template previews) it is a plain "Live list: ..." line. Nothing server-side knows about it, so list rows never become `page_links`, backlinks or graph edges (`ParseWikiLinks` finds no `[[ ]]` in the line); `codexPlainExcerpt` and `graphExcerpt` skip `{{list ...}}` lines, and `fillTemplate` still replaces only the exact `{{title}}` and `{{date}}`.
- Codices unlinked mentions (`api/codex_mentions.go`, `FindMentions`/`LinkMentions` in `db/codex_links.go`, `GetCodexBodies`): `GET /api/codices/pages/{id}/mentions` (See) lists the other pages of the codex that name the page's title or an alias in plain text and don't link to it (backlinks and the page itself are left out; at most 50 pages, `total` counts all; two snippets of ±60 characters each); `POST .../mentions/link` `{from_page_id, base_revision}` (Edit; the from page must be in the same codex, else 400) rewrites that page's body and saves it through `saveCodexRevision` with the note "Linked mentions of {title}" (stale base 409 `stale_base`, nothing found 200 `{linked: 0}`). No SQL prefilter: bodies are scanned in Go because SQLite's case-insensitive matching is ASCII-only. Rules: names deduped by `NormName`, under 3 characters or containing `[`, `]` or `|` skipped, spaces/tabs inside a name match any run of whitespace except newlines, case-insensitive whole words (no letter, digit or `_` either side, checked by hand), longest name first, no overlaps; never matched inside `[[...]]`/`![[...]]`, fenced code, inline code, `[text](url)`, bare URLs or `{{list ...}}` lines. A mention written exactly as the title becomes `[[Title]]`, anything else `[[Title|as written]]`. The page screen loads the "Mentioned, not linked" box after the page (`loadMentions`), like the local graph.
- Codices quick notes (`api/codex_notes.go`, `db/sqlite_codex_notes.go`): `codex_notes (id, codex_id, user_id, body, created_at)` are private to their author, one inbox per user per codex (body 1-5000 characters after trim, at most 200 per user per codex: 409 `inbox_full`); nobody else ever sees them, and someone else's note is a 404 `note_not_found`, never a 403. Routes: `GET`/`POST /api/codices/c/{id}/notes` (the caller's own, newest first; `POST` `{body}` gives 201 `{note}`), `PUT`/`DELETE /api/codices/notes/{id}`, `POST /api/codices/notes/{id}/append` `{page_id}`. Rights: listing and deleting need only See (someone demoted to See can still read and clear their inbox), adding, editing and filing need Edit; the notes stay stored when access is lost. Filing runs in one transaction: `append` (`AppendNoteToPage`) adds a blank line, `_Nov 21, 2026 · Name_` (the `templateToday` date style and the display name) and the note to the end of a page of the note's codex (else 400), saves a revision noted "Added a quick note" and deletes the note (404 `page_deleted` keeps the note); `POST /api/codices/pages` with `note_id` builds the body as the filled template, a blank line and the note (articles only) and `CreatePageWith` deletes the note in the same transaction (`createPageWithTx`), rolling back when the note isn't the author's or is from another codex. Cascades are by hand: `DeleteCodex` and `AnonymizeUser` delete the notes. The codex payload has `note_count` (editors only, for the Inbox badge); the inbox screen is `/codices/c/{id}/inbox` (a last segment `inbox`, like `graph`), the Note button and `n` key open the `quickNote` dialog (local draft `codex-quicknote:{codexId}`), and a game's `codex` object has `can_edit` so `game.html` can offer the same note.
- Codices link from selection and missing pages (`linkSelection` in `static/codex-editor.js`, `codexNewMissing` and `openCreateMissing` in `static/codex.js`): `Mod-k` and the Link button wrap the trimmed selection (one line, at most 120 characters, no `[`, `]` or `|`, else a toast and nothing changes) as `[[Title]]` when a page has that exact title, `[[Title|as selected]]` for another case or an alias (compared with `codexNorm`, titles before aliases), else `[[as selected]]`; `createCodexEditor` returns `{view, linkSelection}`. After a 201 save, link targets that resolve to no page or alias and weren't targets in `draft.initial.body` (`![[` embeds skipped, deduped, at most 20) open the `createMissing` dialog: a row per title with folder and template selects (the saved page's folder and its default, re-picked on a folder change until that row's template was touched). It is client-only: the page is already saved (`saved` stays true, the draft is cleared), Save and create POSTs `/api/codices/pages` once per ticked row in turn and shows a failure on its row without stopping the rest, and Just save, Esc and the backdrop all leave for the page with `?saved=N`, plus `&created=N` for the arrival toast.
- Codices user mentions (`api/codex_users.go`, `LinkUsernames` in `db/codex_links.go`, `userMenu` in `static/codex-editor.js`, `CODEX_USER_RE` in `static/codex.js`; design `docs/design/codex-user-mentions.md`): `@[Name](userId)` in a body is a mention; the id is the reference and the name only a snapshot (`mentionLabel`). The editor's `@` list offers every non-deleted account (`GET /api/codices/users`, See) and inserts that text; the server does the same for a typed `@username` in `handleSavePage`, `handleCreatePage` (the filled template and note included) and filing a quick note, never on restore, copy or template save, and never inside `mentionMask` spans. Readers see a link to `/profile?user_id=` under the current display name; an id missing from the user list (deleted) is plain `@Name`. Mentions are not `page_links`, send no notifications, and have nothing to do with "unlinked mentions" (page titles).
- Codices / menu (`slashMenu` in `static/codex-editor.js`, `CODEX_SNIPPETS` and `codexSlashItems` in `static/codex.js`): a second completion source beside the `[[` one, fed by the `slash: () => [{label, detail, section, keys, text, cursor}]` option. It fires only on `/[\w-]{0,20}` at a line start or after whitespace (URLs and "and/or" never trigger it); the library can't filter a `/` prefix, so the source filters on label + keys itself (`filter: false`) and `apply` replaces the `/` too. Items: Today's date (the server's `today`, same as `{{date}}`), Person, Callout, Loot list, Live list, Divider, then "{name} headings" for each built-in and codex template that has `##` headings (loaded once in `initDraft`). The Insert / toolbar button dispatches a `/` as an `input.type` event so the menu opens (the bundle doesn't export `startCompletion`). A line that is only `---` renders as `<hr>` in `codexMarkdown` only, not in the shared `renderMarkdown`; both excerpt builders skip it.
- Discord (optional; design `docs/design/discord-notifications.md`; `discord/` REST client, `api/discord*.go`, `db/sqlite_discord.go`): on when `DISCORD_BOT_TOKEN` is set (`discordEnabled`); linking also needs `DISCORD_CLIENT_ID`, `DISCORD_CLIENT_SECRET` and `PUBLIC_URL` (`discordCanLink`; `PUBLIC_URL` is also the base of every link in a message, none without it). Everything goes through the `discord_outbox` table and one sender goroutine (`StartDiscordSender`, woken by `wakeDiscord`, backoff up to 6h, then `failed`; failed rows are pruned after 7 days), never inline in a handler. `notify()` is the one hook: after it writes the inbox batch it calls `queueDiscordDMs`, which renders the text once (`discordText` mirrors `message()` in `static/notifications.js`; keep them in step) and queues one DM per linked recipient whose toggle for `discordGroup(type)` is on; `notify` returns how many rows it wrote (-1 on error). Game channel posts are `postToChannel` wrappers called next to the matching `notify` (not for finished/cancelled games but the status change, not for events the admin switched off in `app_settings` `discord_channel_events`). The session reminder (`remindUpcomingSessions`, 24h before, not for sessions confirmed later than that) dedupes through `notifications.type = 'session_reminder'`; when nobody got an inbox row it writes a `user_id ''` marker row so the channel post isn't repeated. `campaigns.discord_channel_id`/`discord_channel_name` are written only by `SetCampaignDiscordChannel` (admin route `PUT /api/admin/discord/games/{id}`, checked against `PostableChannels`), never `SaveCampaign`; changing the guild clears them all. A 10003/50001 on a channel post clears the game's channel and sends admins `discord_channel_lost`. Foreign keys are off, so `AnonymizeUser` deletes the `discord_links` row and the user's DMs, `DeleteCampaign` its queued rows, and disconnect/relink drop queued DMs by hand. OAuth keeps its state in the cookie session (`middleware.SetSessionValue`/`TakeSessionValue`). `DISCORD_API_BASE` is only for E2E (`e2e/fake-discord.js` on port 18081).
- Admin pages are separate pages under shared tabs: `/admin/users`, `/admin/access`, `/admin/systems`, `/admin/integrations`, `/admin/discord` (the `.admin-tabs` markup is copied in each; shared styles in `static/admin.css`). `GET /api/admin/integrations` lists unblocked users with their calendar link and Discord link, never the calendar token. A calendar token can't be turned off, so "in use" comes from `calendar_tokens.last_read_at`: `HandleCalendarFeed` sets it on GET (at most once an hour) and `SetCalendarToken` resets it.
- Uploads: map images live in `UPLOAD_DIR` (default `uploads` next to the database file, so on the Docker data volume); files are random-named and immutable, restoring an image adds a row for the same file, and the backup job mirrors new files to `BACKUP_DIR/uploads` without deleting. Codex attachments live in the `attachments/` sub-folder and are not mirrored or backed up. CodeMirror, Leaflet and d3-force are vendored by `tools/vendor` (d3-force's ISC licence, which also covers d3-dispatch, d3-quadtree and d3-timer, is copied to `static/vendor/d3-force/LICENSE`) (`npm run build` there; outputs are committed under `static/vendor`, and `tools` is in `.dockerignore`).

## Conventions

- Go: handlers named `HandleXxx`; always set `Content-Type: application/json` and an explicit status; decode bodies with `json.NewDecoder(r.Body).Decode(&v)`; guard methods with `r.Method` checks.
- JS: `fetch()` only, except `codexUpload` (XHR, for upload progress); wrap calls in try/catch and report via `showMessage(text, 'error')`; use `textContent` (or `escapeHtml()`) for user-generated content; init on `DOMContentLoaded`.
- Styling follows `STYLE_GUIDE.md` ("Scriptorium": parchment/candlelight themes via CSS tokens, Inter + Barlow Condensed, IM Fell for page titles and the main nav, IBM Plex Mono only in Markdown editors, rubric-red accent that means "you"; mock-ups in `docs/design/mockups/`). Read it before UI work. Bump the `?v=N` cache-busting query on CSS links when changing CSS.
- Keep the app lightweight and minimal: surgical changes, reuse existing helpers before adding abstractions, no broad refactors unless asked.

## Git

- Commit and push each finished logical chunk as you go, without being asked (`commit-as-you-go` skill). Never commit directly to `main`. Commit subjects: lower case, ≤6 words, **no** `feat:`/`fix:` prefixes; put details in the body. Small logical commits.
- Branches use type prefixes: `feat/...`, `fix/...`, `chore/...`; worktrees go under `.claude/worktrees/` with matching names (`feat-...`).
- PRs are squash-merged with titles like `feat/admin users`.
