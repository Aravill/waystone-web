# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Waystone Web: Go (stdlib `net/http`, SQLite via `modernc.org/sqlite`, local username/password auth) backend + plain HTML/JS frontend in `./static` (no build step; Alpine.js vendored at `static/vendor/`). MVP scope and progress: `docs/mvp.md`.

## Commands

- `.env.example` must list every env var the code reads (`os.Getenv`), with required/optional and defaults. Update it whenever you add, rename, or remove one, and keep `docker-compose.yml`'s `environment:` in sync.
- Run locally: `go run main.go` → http://localhost:8080. Set `SESSION_SECRET` (required, ≥32 chars, e.g. `openssl rand -base64 32`; the server exits without it) and `ADMIN_PASSWORD` per `.env.example`; without `ADMIN_PASSWORD` the server starts but the admin can't log in. Add `SEED_DEMO_DATA=1` to get demo users/campaigns/sessions on an empty DB (users `testy`/`roy`/`adam`/`simon`, password in `config.InitialPasswords`); off by default, local dev only.
- Verify changes: `go build ./... && go vet ./...`. Frontend E2E tests use Playwright in `e2e/`: `npm ci`, `npx playwright install chromium` (once), `npm run test:e2e`. They start their own server on port 18080 with a throwaway DB in `e2e/.tmp` (via `DB_PATH`) and never touch `./data`. PRs to `main` can't merge unless the `playwright` check (`.github/workflows/e2e.yml`) passes. There are no Go tests or linters; add E2E tests only for stable, high-value flows.
- `./deploy.sh` deploys production (app + Caddy HTTPS for waystone.aravill.org via `docker compose --profile prod up -d --build`) and keeps the data volume; never run `docker compose down -v` against data worth keeping (it wipes the SQLite volume). SQLite snapshots go to `./backups` (`BACKUP_DIR`).
- For local Docker testing use `/deploy-local` (`up`/`down`/`status`), not `docker compose up`: plain compose names the project after the folder, so every worktree leaves its own image and volume behind.
- Static files are copied into the Docker image, so frontend changes need `docker-compose build --no-cache`.
- Local DB lives at `./data/waystone.db` (gitignored); `DB_PATH` overrides it.

## Architecture gotchas

- Routes are registered in `api/router.go` (not `main.go`, despite the README). `/` is auth-wrapped and serves `dashboard.html` (Home, fed by `GET /api/agenda` in `api/agenda.go`), so every root-level JS/CSS file a page loads must get its own `http.HandleFunc` entry there, or be referenced under `/static/...`. Home also loads `/campaigns.js` for the shared helpers (`replyWord`, `zoneAbbr`, `formatShortDate`, `userAvatarHtml`).
- App version is baked in at build via ldflags (`config.Version`, `APP_VERSION` build arg). The Deploy workflow computes it from the PR-title prefix (`feat/` bumps minor, else patch) and tags after a successful deploy, so keep the `feat/` prefix accurate.
- DB access goes through the `Store` interface in `db/store.go`: add the method to the interface, implement it on the SQLite store, and expose a package-level wrapper in `db/` that calls `GetStore()`.
- Protect routes with `middleware.AuthMiddleware`; use `middleware.GetSession()` / `ClearSession()` for session state.
- Accounts start with no password (`password_hash=''`, `must_change_password=1`). Admin create and reset call `issueInvite`, which returns a one-time token valid for 7 days; only its SHA-256 hash is stored in `password_invites`, one per user. `/invite/` and `/api/invite/` are public, outside `AuthMiddleware`. An invite is valid because its row exists, never because of `must_change_password`, and `/change-password` only remains for users still holding an old temporary password.
- `AuthMiddleware` adds `?next=<page>` when redirecting a logged-out page request, and `login.html` only follows it if it's same-origin. Page loads (not API calls) renew the session cookie at most once a day via `renewed_at`.
- User display name precedence: `Nickname` → `Name` → `Username` (`User.DisplayName()`). API responses that reference users keep raw IDs and add enriched `*_user` / `*_users` objects (mirror the campaigns API).
- Session responses are one per `(session_id, user_id)` (upsert); pending players are computed from the campaign's player list.
- When changing `models/user.go`, update seed data in `config/config.go` and keep `SaveUser` and the `SELECT`/`Scan` sites in `db/sqlite_store.go` in sync.
- The `ADMIN_USERNAME` user is env-managed: password reset from `.env` on every start; can't be blocked, deleted or demoted.
- The session cookie is `Secure` by default (`SESSION_COOKIE_SECURE`): fine on `http://localhost`, but over plain HTTP on a LAN IP login returns 200 and the cookie silently never sticks; set it to `false` there.
- Journal entries key on the session id (`journal_entries.session_id`), never on a session number: numbers are positional (`campaignSessionSummaries`, computed per request) and shift when a session is recorded, deleted, re-dated or cancelled, so never store one (not in a revision, notification or seed). Entries exist only for played sessions (Confirmed and ended, or by hand): `journalSession` in `api/journal.go` is the one check. Foreign keys are off, so the cascades are by hand: `DeleteCampaign` and `DeleteManualSession` delete contributors, revisions, then entries via `deleteJournalForSessions`. Saves are optimistic (`entry_id` + `base_revision`, 409 on a stale base) and the newest 200 revisions per entry are kept; credit lives in `journal_entries.author_id` and `journal_contributors`, so it survives pruning. A cancelled session's entry stays readable and deletable (`journal_cancelled` on the game API) but not editable.
- Characters: assignments are ended (`ended_at`), never deleted, on leave/kick/decline/anonymize/swap/clear. Foreign keys are off, so `DeleteCampaign`/`DeleteCharacter` delete assignments by hand, and any new code that removes a player from `campaigns.players` must end their assignments (`endUserAssignments`, same tx). A game accepts characters only when `campaignSystemID` resolves its system text to a known system. `notify` accepts a nil campaign. A character has an optional `codex_url` (set by its owner in the create/edit forms), shown as a "Codex page" button on the character page; `validCodexURL` in `api/characters.go` is the only server check (`https://waystone.aravill.org/codices...` only, exact host, no port/userinfo, or `/codices...` on the local host the request came to, so dev/E2E work; 400 otherwise; saved as `url.URL.String()` with the host lower-cased: path must equal its `path.Clean` form, bar one trailing slash, so `//codices` and `..` are refused; at most 2000 characters after percent-encoding), and `safeCodexUrl` in `static/characters.js` re-checks on the client before rendering a link. Design: `docs/design/characters.md`.
- Sessions with `manual=1` (the DM's "Record a past session") are chronicle-only: excluded from the month view and ICS, no replies or notifications, and may have `time=''` so `sessionStart` fails; check `Manual` before calling it.
- The Calendar button focuses the first unanswered session's month, so tests use `openCalendar`/`goToMonth` helpers, not `page.clock`.
- `api.StartSessionStartNotifier(ctx)` (started from `main.go`) runs every minute and sends one `session_started` notification per Confirmed session to its players and followers (never the DM) once it begins. The `notifications` table is the dedupe, so there is no schema or env var for it.
- Codices (`/codices`, `api/codex*.go`, `db/sqlite_codex*.go`, `static/codex*.js`): a codex is a folder of pages and every page belongs to one (`pages.codex_id`; there is no Unsorted folder, creating or moving a page needs an existing codex). Old URLs `/codex`, `/codex/w/...` and `/codex/p/...` 301 to `/codices`, `/codices/c/{id}` (a codex) and `/codices/p/{id}/...` (a page); the API is `/api/codices` (`GET` home, `POST` create), `/api/codices/c/{id}`, `/api/codices/pages/...`, `/api/codices/folders/...`, `/api/codices/titles?codex=`. The schema used to say `worlds`/`world_id`: `renameWorldsToCodices` renames them in place before the CREATE block, and `rescueUnsortedPages` moves any page left with `codex_id ''` into a codex named "Unsorted pages". `[[Title]]` links and map pins resolve only inside the page's own codex, by title or alias (compared with `NormName`, never SQL NOCASE), and are stored in `page_links.to_page_id` / `map_pins.to_page_id`. Anything that changes what a name can point at (create, rename, alias set, move, delete a page) must end its transaction with `resolveCodexLinks(tx, codices...)` for the codices it touches (the page's codex; a move passes the old and the new one), and `loadCodexIndex` takes the same optional codex filter, so a save never reloads every codex; a body save only rebuilds that page's rows. Foreign keys are off: `DeletePage` removes revisions, contributors, aliases, links, pins, pin events and images by hand (the handler then removes the image files), and `DeleteCodex` is refused (409 `codex_in_use`) while a page is in it; games don't block it, it clears their `campaigns.codex_id`. `campaigns.codex_id` is a label written only by `SetCampaignCodex`, never by `SaveCampaign`; the game API sends `codex_id` and `codex` `{id, name}` and `game.html` shows it as a label (a link when `codex.can_open`). Maps are hidden for now: `codex.html` doesn't load `codex-map.js` or show any map, pin or games UI, but the tables, the `/api/codices/pages/{id}/...` map routes and the upload/backup code stay. Maps are an optional part of any page, not a page kind: `pages.kind` is always `lore` (a startup `UPDATE` folds old `'map'` rows in; nothing branches on it) and the API sends `has_map` instead. A page's map is its newest `map_images` row (history ordered `created_at DESC, rowid DESC`), pins are `map_pins`/`map_pin_events` keyed by `map_page_id` (the page), and pins count as backlinks (`via` `pin`). "Remove map" (`DELETE /api/codices/pages/{id}/map`, `RemoveMap`) deletes the pins in one tx, logging a `remove` event each, and inserts a marker `map_images` row with `file=''`: a newest row with an empty file means no map, the marker is hidden from the image list, `DeletePage` skips it, and restoring an older image (a new row) brings the map back, while the removed pins return only by undoing their events in History. Pins, pin undo-of-remove and map removal need a current image (409 `the page has no map`). Folders (`codex_folders`, `pages.folder_id`) nest inside a codex and are only for sorting: links, title/alias uniqueness and revisions ignore them, folder names are unique among siblings by `NormName`, and a page's folder must be in its codex (`MovePage` resets it). folders nest up to 10 levels (`db.MaxFolderDepth`, 400 on create/move beyond it), a missing parent is 400 `parent_not_found` while a missing edited folder is 404 `folder_deleted`, and PUT takes `name` or `parent_id`, not both. `DeleteFolder` re-parents its sub-folders and pages one level up by hand (refused if a sub-folder's name clashes in the parent), and `DeleteCodex` removes the codex's folders. Page saves are optimistic (`base_revision`, 409 `stale_base`), titles change only through rename (which rewrites links in the same codex and adds revisions), and restoring a revision restores the body only. `codex.html` also loads `journal.js` for `diffWords`/`diffHtml`, so `codex.js` must not redeclare its top-level names.
- Codices access rights (admin page `/admin/access`, `api/admin_access.go`): `user_rights (user_id, action)` holds `codices.see` / `codices.edit` (`models.RightCodicesSee`/`RightCodicesEdit`; generic so more actions can be added) and `codex_access (codex_id, user_id, level)` holds `see` or `edit` per codex; admins need no rows and always pass, new users get nothing, and `CreateCodex` inserts its creator's `edit` row in the same tx (not for admins, so no hidden row outlives a demotion) (`DeleteCodex` and `AnonymizeUser` clear them by hand). `api/codex_access.go` is the one place for the rules: `loadCodexRights(userID)` gives a `codexRights` with `canSee/canEdit(codexID)` (edit implies see; nothing without `codices.see`) and `canManage()` (Edit Codices: create codices, rename or delete ones the user can see); handlers call `codexRightsFor` then `checkCodex/checkPage/checkFolder(w, id, edit)`, which answer 404 when the codex or page isn't visible (never leak existence) and 403 when it is visible but not editable (moving a page needs Edit on both codices; an unknown or invisible target is 400 `codex not found`). `codexGate` hides `/codices*` and `/api/codices*` (404 / redirect to Home) from anyone without See Codices, `/auth/current-user` returns `codex_access` from the same check, and `theme.js` reveals the `[data-codex]` links (which start `hidden`) only when it's true. The home, codex and page payloads add `can_create` / `can_manage` / `can_edit` for the UI, `titles`, home and recent changes list only visible codices, and `files/{name}` needs See on the codex of the page that owns the image. A game's `codex` object has `can_open` (the viewer can see it); a DM can only set `codex_id` to a codex they can see. Codex names are unique across all codices, so a 409 `codex_name_taken` tells someone with Edit Codices that a codex of that name exists (accepted). `SEED_DEMO_DATA` grants the demo users See Codices, Edit on the demo codex for Roy and Testy, and Edit Codices for Roy.
- Codices tags (`api/codex_tags.go`, `db/sqlite_codex_tags.go`): `codex_tags (id, codex_id, name, ...)` belong to one codex and `page_tags (page_id, tag_id)` joins them to pages; names are 1-40 characters on one line and unique per codex by `NormName` (409 `tag_name_taken`), anyone with Edit on the codex creates, renames and deletes them (`GET`/`POST /api/codices/c/{id}/tags`, `PUT`/`DELETE /api/codices/tags/{id}` through `checkTag`, `PUT /api/codices/pages/{id}/tags` with `{names}` creates the missing ones), tag changes are not revisions, and cascades are by hand: `DeleteCodexTag` drops its `page_tags`, `DeletePage` drops the page's, `DeleteCodex` drops the codex's tags, and `MovePage` drops the page's tags (they belong to the old codex; the move warning says so). The page payload has `tags`, the codex payload has `tags` with `page_count` and each page's `tag_ids`, and `?tag=name` on the codex screen filters the list client-side.
- Codices pictures (`api/codex_pictures.go`): `page_images (id, page_id, name, file, width, height, uploaded_by, created_at, removed_at)` plus `pages.cover_image_id` (added with the ALTER-if-missing pattern) hold images written `![[name|caption]]` (the caption may be empty); a picture belongs to its page and follows its codex's rights. The routes are `GET`/`POST /api/codices/pages/{id}/pictures` (raw body, original file name URL-encoded in `X-File-Name`, same `receiveCodexImage` as map images: PNG, JPEG, WebP or GIF, 25 MB; `gifFramesFit` walks a GIF's blocks without decoding and refuses frames outside the screen, truncated files and more than 1000 frames, because `DecodeConfig` only reads the screen size), `DELETE .../pictures/{imageID}` and `PUT .../cover` `{image_id}`; they are "pictures" because `.../images` already is the page's map history. `name` is the sanitised file name, unique within the page including removed ones (" (2)" before the extension). Remove is soft (`removed_at`): the row and file stay so old revisions and any `![[name]]` still in the text keep rendering, so the page payload's `image_index` lists every picture ever uploaded by name while `images` lists only current ones; a removed picture can't be the cover and removing the cover clears it. `DeletePage` deletes its picture rows and files. `db.UploadFileRe` (which also gates serving, removal and the backup mirror) accepts `png|jpg|webp|gif`, and `GetImageCodexID` looks in both `map_images` and `page_images`, so `files/{name}` needs See on the page's codex. `ParseWikiLinks` skips a `[[...]]` that follows `!`, so picture embeds are never links or wanted pages; the JS regexes (`CODEX_LINK_RE`, `CODEX_IMAGE_RE`, the editor's) mirror it, and `codexMarkdown` swaps pictures for placeholders before links.
- Codices templates and copying (`api/codex_templates.go`, `db/sqlite_codex_templates.go`): `codex_templates (id, codex_id, name, description, body, created_by, created_at, updated_at)` and `codex_template_tags (template_id, tag_id)` join a template to tags of its codex by id, so saving a template creates the tags it names that the codex lacks, `DeleteCodexTag` drops the join rows, and `DeleteCodex` deletes the codex's templates (they never block it). A name is 1-80 characters, unique per codex by `NormName` in Go (409 `template_name_taken`); the description is at most 160, the body is limited like a page's, and templates have no history. Anyone with Edit on the codex creates, edits and deletes them (`GET`/`POST /api/codices/c/{id}/templates`, `PUT`/`DELETE /api/codices/templates/{id}`; See lists them). The nine built-in templates are Go data (`builtinTemplates`, ids `builtin:session` and so on, the same in every codex, never stored); `GET /api/codices/templates/builtin` returns them with `today`. `POST /api/codices/pages` takes `template_id` (a built-in, or a template of the same codex, else 400): the server then ignores `body` and writes the template's text and tags in one transaction (`CreatePageWith`). `{{title}}` and `{{date}}` (written "Jan 2, 2006", UTC) are the only placeholders, filled in one pass by `fillTemplate` (the client's `fillTpl` mirrors it for the preview, using the server's `today`). "Save as template" is computed in the browser (`codexHeadingsOnly`: the `##`/`###` lines outside code fences; or all the text without `![[...]]` pictures) and posted to the template endpoint. `POST /api/codices/pages/{id}/copy` needs See on the source and Edit on the target (an unseen target is 400 `codex not found`, a see-only one 403): the copy is a new page with its own history starting at revision 1 with the note "Copied from <title>", without aliases, with `[[links]]` as written (resolved in the target codex by the create transaction), the tags by name with `copy_tags` (missing ones created), and with `copy_images` each current picture's file duplicated under a new random name (`duplicatePictures`; picture names and the cover are kept, removed pictures the body still embeds are duplicated too with their `removed_at`, the copier is recorded as uploader, and the new files are removed again if the insert fails; a cheap `CheckNewPage` runs first so a refused copy duplicates nothing). Built-in template names are reserved: creating or renaming a template to one is a 409 `template_name_taken`. The New page dialog has no codex select (it creates in the current codex) and remembers the last template per codex in localStorage.
- Codices graph (`api/codex_graph.go`, `db/sqlite_codex_graph.go`, `static/codex-graph.js`): `GET /api/codices/c/{id}/graph` (See right, 404 otherwise) returns `nodes` (pages plus a synthetic `missing:<normalized text>` node, `missing: true`, per link target without a page, with top folder, folder path, tag names and a plain excerpt), `links` (`source`, `target` from `page_links`, A to B and B to A both kept; the client draws one line per pair) and `top_folders` (name order, which fixes the colours); it runs three queries and leaves out map pins. The graph screen is `/codices/c/{id}/graph` (`?from={pageId}` rings that page): in `parseRoute` a last segment `graph` right after the codex id always means the graph screen, so codex links never carry a slug (a codex named "Graph" still works). The layout is `d3-force` vendored through `tools/vendor` (it now builds two bundles: `codemirror.bundle.js` and `d3-force.bundle.js`, global `D3F`), loaded lazily by `codex-graph.js` and drawn as plain SVG; node positions are not saved. The page screen's Local graph box (hidden when the page has no links) uses `GET .../graph?around={pageId}`: that page, its direct neighbours in both directions and the links among them, without excerpts (404 when the page isn't in that codex); the client shows at most 30 neighbours.
- Uploads: map images live in `UPLOAD_DIR` (default `uploads` next to the database file, so on the Docker data volume); files are random-named and immutable, restoring an image adds a row for the same file, and the backup job mirrors new files to `BACKUP_DIR/uploads` without deleting. CodeMirror, Leaflet and d3-force are vendored by `tools/vendor` (d3-force's ISC licence, which also covers d3-dispatch, d3-quadtree and d3-timer, is copied to `static/vendor/d3-force/LICENSE`) (`npm run build` there; outputs are committed under `static/vendor`, and `tools` is in `.dockerignore`).
- Log out and Profile live in the header's user menu (`<details class="user-menu">`), not the nav; every page with a nav must include it and call its own logout handler (`admin-users` uses `logout()`). `.message` is a fixed toast, so pages show it with `x-show` and `role="status"`.

## Conventions

- Go: handlers named `HandleXxx`; always set `Content-Type: application/json` and an explicit status; decode bodies with `json.NewDecoder(r.Body).Decode(&v)`; guard methods with `r.Method` checks.
- JS: `fetch()` only; wrap calls in try/catch and report via `showMessage(text, 'error')`; use `textContent` (or `escapeHtml()`) for user-generated content; init on `DOMContentLoaded`.
- Styling follows `STYLE_GUIDE.md` ("Scriptorium": parchment/candlelight themes via CSS tokens, Inter + Barlow Condensed, IBM Plex Mono only in Markdown editors, rubric-red accent that means "you"; mock-ups in `docs/design/mockups/`). Read it before UI work. Bump the `?v=N` cache-busting query on CSS links when changing CSS.
- Keep the app lightweight and minimal: surgical changes, reuse existing helpers before adding abstractions, no broad refactors unless asked.

## Git

- Commit and push each finished logical chunk as you go, without being asked (`commit-as-you-go` skill). Never commit directly to `main`. Commit subjects: lower case, ≤6 words, **no** `feat:`/`fix:` prefixes; put details in the body. Small logical commits.
- Branches use type prefixes: `feat/...`, `fix/...`, `chore/...`; worktrees go under `.claude/worktrees/` with matching names (`feat-...`).
- PRs are squash-merged with titles like `feat/admin users`.
