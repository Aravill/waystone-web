# Minimal Viable Product
## Summary
This document describes what must-have features are to be implemented before presenting this website to the waystone server members
## MVP Requirements
- [x] Calendar & Session Planning
    - [x] DM can suggest session dates
    - [x] Players can react with confirm / reject / tentative the dates
    - [x] DM can see who reacted how
    - [x] Dates can be cancelled
    - [x] DM can copy a session and paste it onto several days at once
    - [x] Calendar sync - the players & DM can import events into their google calendar
- [x] Signing up
    - [x] Users can sign up for campaigns if sign-ups are open
    - [x] DMs can accept or ignore signed-up players
    - [x] Ignored players do not show up for the DM anymore unless a special button is clicked
    - [x] Users can withdraw a pending sign-up or leave a campaign they're playing in (the DM is notified)
- [x] Following
    - [x] Users can follow campaigns (to receive notifications)
    - [x] Players are automatically following campaigns they're in
- [ ] Notifications
    - [x] Inbox in the header with unread badge, mark read / mark all read
    - [x] Followers notified of campaign status changes and suggested / confirmed / cancelled sessions
    - [x] Players notified of accepted / declined sign-ups and removal
    - [x] DMs notified of new sign-ups and auto-closed sign-ups
    - [x] Campaign cards highlight pending actions (unanswered suggested sessions for players, pending sign-ups for the DM)
    - [ ] Discord bot DMs - users link their Discord account (OAuth2) on the profile page and receive their notifications as DMs from a Waystone bot (opt-in, sent in the background)
- [x] Administration
    - [x] Always one super admin role
    - [x] An admin / super admin can add or remove people from the access whitelist
    - [x] A super admin can make other people admins
    - [x] Admins can remove any campaign (only admins: DMs can edit but not delete their games)
    - [x] An admin can revoke whitelist access to a user (doesn't delete the account, just blocks their log-in)
    - [x] An admin can delete accounts
    - [x] Admin can add/remove players to games
- [x] Campaigns
    - [x] Standard operations
        - [x] Creating
        - [x] Updating
        - [x] Deleting
    - [x] Switching states according to the state transition map
    - [x] Removing active players
    - [x] Admins can issue one-time invite links so players set their own password
    - [x] Opening / Closing sign-ups
    - [x] Toggling sign-up auto close and auto open - not needed: disabled by leaving the desired player count blank, and bypassed by manual opening/closing of sign-ups
    - [x] Campaign grid view
    - [x] DMs are colorfully distinct from players
    - [x] Visually distinct campaign statuses
    - [x] Campaign types (and their visual distinction) - Campaign, Adventure, One-shot
    - [x] Game systems - admins manage known systems (optional logo); campaigns pick one or type a custom one; shown on the campaign card
    - [x] Game page - sheet with the full description (basic Markdown), the chronicle (upcoming sessions as calendar cells, played sessions with attendees) and a side panel for the selected session or the company (visible to all users; replies and rolls are for members)
    - [x] Reply to suggested sessions from the game page
    - [x] DMs record past sessions by hand (optional times, ticked attendees, named guests), edit and delete them
    - [x] Characters - players keep a roster per system and assign one per game (history kept, shown in the chronicle); see `docs/design/characters.md`
- [x] Profile
    - [x] Standard operations
        - [x] Changing nicknames
        - [x] Updating avatars
        - [x] Deleting account (anonymizes them)
    - [x] List of campaigns playing in and dungeon mastering
    - [x] Visually distinct campaign statuses
- [x] Initial log-in
    - [x] Profile creation process (set nickname and avatar)
- [x] Codex
    - [x] Worlds as folders (plus a shared Unsorted folder), pages (each optionally with a map) with `[[Title]]` links, aliases, revision history and restore
    - [x] Maps with an uploaded image, pins that point at pages, and an undoable pin log; see the Codex section of `STYLE_GUIDE.md`
    - [x] Folders inside a world (nested, up to 10 levels, collapsible tree), a page layout with a contents rail and summary box, and `CODEX_ADMIN_ONLY` to limit the Codex to admins while it is tried out
- [x] Technological
    - [x] SQLite
    - [x] Alpine.js
    - [x] Code review skill
- [x] Misc
    - [x] Waystone logo on the page
